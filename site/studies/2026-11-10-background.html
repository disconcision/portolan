Background research

The findings behind the first scope notes: what carries over from Hazel, how an outside process can watch a coding agent, what OCaml tooling gives, and who else is near this.

Gathered in one day by research agents reading source and public documentation. Nothing here was built or measured. Version numbers, licences and feature claims are as reported on that day and were not checked a second time. The last section lists what could not be confirmed.

Hazel's canvas

The Constellation canvas lives on Hazel's agent-canvas branch, in src/web/app/canvas/. It is about 27,300 lines including CSS.

Input. One function, CanvasGraph.extract, is the boundary between Hazel's statics and the graph. Everything after it reads a record of type nodes, function edges, values and tests. To build that record you need: ordered top-level and module-member items with their module path; each type alias with its body and constructors; each binding's name and type, flattened to arguments and result; doc comments; an error flag and a hole flag per definition; references to other top-level names; tests with status and the functions they mention; and a stable handle per definition.

Events. Per agent step the canvas needs a snapshot of that record, a cause label, and optionally a site and an ok or error state. It never reads edit operations. Each released beat is diffed against the previous layout, planned into a score of acts (appear, form, draw, pill, reveal, vanish, erase, change, drift, ripple, say), validated, then played. Traces today store tool calls and replay them through the real handler, so they hold no snapshots.

What lifts. Nearly verbatim: layout engine, score, camera, Trine, bubbles, ripple, jelly, animation, CSS. With a thin adapter: geometry, view and player, once the graph record's types are split from extraction and its id and term fields made opaque. To rewrite around the same shape: trajectories, the beat buffer, and the diff-to-score block of about 500 lines inside the sidebar. Rendering is virtual_dom plus direct DOM and Web Animations; Bonsai appears in three calls.

Not built there: fog of war, columnar module sub-layouts, per-submodule collapse, agent-sourced selection, and the exploded string-diagram view of a function.

Hazel's editing core

On the modular-editors branch. One kernel serves the outline sidebar and the agent's tools.

  • Operations. Insert, replace, delete and move, in one all-or-nothing transaction. Sources are text, a template, a copy, or a single token with its id kept. Duplicate, rename and change of kind are derived. A refusal names a reason and the failing operation.
  • Paths. M/parse, M/"hint" for a hinted test, test#2 for the second of a kind, f/=> for a block's result, and parts :pattern, :definition, :head. The resolver works on syntax alone.
  • Agent tools. insert, replace, delete, move, rename, open, close. Results name changes by path, then list static errors and tests whose status changed.
  • Checks, once per reply. Dangling uses of a deleted entry, rename capture, rebinding on replace, and no new errors. Any failure restores the start of the reply.
  • Agent view. A code map with bodies folded and notes as comments (uses, errors, test status), with open entries in full below it. The exact text of each request is recorded, and View as agent replays it.
  • A/B, October. Six tasks, old tools against new. Opus finished all six either way, with about 22% fewer input tokens and 30% fewer calls on the new verbs. Lessons: show example code fenced, drop the :body part, make refusals say what went wrong, stop repeated identical failures, prefer hints to index paths.

The Agent Client Protocol carries tool calls with locations and diffs, and many agents speak it directly or through an adapter, so a client or proxy on it covers the long tail.

For an observer that does not care which harness: a file watcher plus a native analysis process as ground truth; a thin hook adapter for attribution; an ACP client later. Ship definition-level tools as an MCP server, which every harness above accepts except pi.

For embedding a harness later: OpenCode fits custom tools plus a custom web UI best. pi is the smallest core to build on. The Claude Agent SDK is the least work if Claude-only is acceptable.

OCaml tooling

  • Merlin and ocaml-lsp. Merlin takes the buffer on stdin, so unsaved and broken files work. Recovery is by design: a recovering parser, and a typer that catches errors per structure item. Commands include outline, type-enclosing, occurrences, holes, construct, errors and locate. ocaml-lsp vendors Merlin and can pass any Merlin command through. _ is a typed hole. Cross-module information reflects the last build.
  • Reason. Merlin reads .re through the Reason reader. The tree-sitter grammars for Reason are stale; the one for OCaml is current.
  • Project-wide occurrences. Need OCaml 5.2 or later and an index built by dune, kept fresh in watch mode.
  • Compiled annotations. A .cmt file is written even on a type error, holding what was inferred. Reading them ties a tool to one compiler version.
  • dune. Watch mode, an RPC interface for diagnostics (documented as experimental), and dune describe for libraries and module dependencies.
  • Existing MCP servers. ocaml-mcp (build status, diagnostics, evaluation; several tools unfinished in 2025) and Tarides' topup (a persistent toplevel). No official dune or Merlin server was found.
  • Values. Lowest effort is expect and inline tests under a watch build. Next is a toplevel loaded with the library.
  • In the browser. merlin-js exists for small playgrounds. For a real dune project with ppx and many libraries, analysis belongs in a native process.

Madhavapeddy on modules and agents

  • OCaml's module language is the perfect fit for agentic programming (October 2026). An agent fills a small well-specified hole better than it handles a large code base. Write and type-check the .mli files for a whole system first, then hand over one module at a time. Abstract types enforce the design: an agent that treats money as a raw integer inside another module is stopped by the compiler. A missing piece of an interface is a signal to revisit the design.
  • Three steps for OCaml to crest the AI humps (OCaml Workshop 2025, with Jaffer, Ludlam and Gibb). The same workflow in three phases: interfaces first and rendered as documentation for human review, then tests that type-check, then implementations one module at a time.
  • In a write-up of porting an HTML5 parser he checks the interface files in a diff separately, to confirm only implementations changed.
  • Tooling from the group: a Claude plugin marketplace for OCaml, odoc-llm module summaries, a devcontainer for sandboxed runs, and monorepo tools so agents can read dependencies locally.
  • Stated pain points: models omit rec, mix integer and float operators, and invent functions; OCaml is a tiny share of training data; ppx needs explaining.

No post was found arguing for functors, or describing signature-level diff review as a tool.

Related work

The scope notes hold the main table. Further items the search returned:

  • Edits and benchmarks. CodePlan (repository-level edits planned over a dependency graph); RefactorBench (multi-file refactoring tasks where baseline agents solve 22%); Diff-XYZ (a benchmark of textual edit formats).
  • Types and proofs. Type-constrained code generation; monitor-guided decoding; agent interfaces for Agda and Rocq built on goals and holes.
  • Review. Kleppmann's argument that people should review specifications while machines check implementations; spec-driven tools such as Kiro and spec-kit, where the reviewed artefact is prose.
  • Change views. difftastic, GumTree and SemanticDiff (syntax-tree diffs shown as text); Softagram (dependency-change diagrams on pull requests); Gource, CodeCity and software cartography (history replays).
  • Definition-level code. Darklang, Lamdu, Pijul.
  • Typed views. GeckoGraph, calligraphy, dune-deps, codept, Glamorous Toolkit, the active Sourcetrail forks.
