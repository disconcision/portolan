An agent canvas for OCaml code bases

A way of working with a code base at a level above the text, with the text always one step down. The starting point is Hazel's Constellation canvas, pointed at ordinary OCaml and Reason projects. What it is for is still being worked out. This page fixes a small first build and sketches where it could go.

In short
  • First build. The parts of Hazel's canvas that translate, for a dune project, with the chat in the same page. It runs from source on new projects and existing ones, its own code included. Next: build Portolan in Portolan, then the Hazel repository.
  • How. A native OCaml sidecar turns the project into the graph record Hazel's canvas already draws, and runs the agent. The canvas code is copied behind that record, free to be shared with Hazel or to diverge.
  • Directions, in a proposed order. Next: working on Portolan in Portolan, something valid to draw, the edited view, layout. Main bets: interfaces, how modules relate, change sets, history, what each agent has seen, several agents. Further out: voice and ink, editing by definition, properties, slices.
  • This page is kept current. It records the scope as it is talked through: your directions, and ones proposed here, marked as such.
Purpose, unsettled

Orders of reading

A working statement, to be revised: the canvas gives a code base several levels, and lets you stay at the highest one that answers your question. Each level shows the one below folded, and opens it on demand, down to the code. It could turn out to be a main way of engaging with code, and the first build should not close that off.

Three things this should not shrink to:

  • Only a first glance. The demo framed it as a first-order alternative to the transcript. The emphasis is better put on having orders at all, and moving between them.
  • Only live. Watching the agent work is the fun part. As a tool it matters as much afterwards: what did yesterday's session do, what is in this branch, what is this code base.
  • Only one agent. The broader subject is people and agents cooperating in one code base, including a few agents at once.
First build

What Hazel has now, for a dune project

Types as nodes, functions as arrows, modules as hulls, tests as pips, Trine, replay, and a click through to the code. Hazel's canvas is about 27,000 lines, of which roughly 15,000 have no Hazel dependencies. Everything downstream of one function, CanvasGraph.extract, reads a plain record, and each step the canvas gets a new snapshot of it with a cause and a site. It never reads edit operations. So the port is a new producer for that record, plus a copy of the Hazel-free code.

Where the graph comes from. The sidecar asks the project's own ocamllsp, which vendors Merlin. It reads .re through the Reason reader, so Hazel works on day one. It recovers from errors one item at a time, so a half-edited file still yields its other definitions. And it is whatever version the project's switch has, so our binary is not tied to a compiler version. dune describe gives libraries. A watch build beside it keeps cross-module types and the occurrence index fresh.

Chat in the same page. The sidecar starts Claude Code in its headless streaming mode and relays it, so the prompt box, the replies and the tool calls sit beside the canvas, as in Hazel. The same stream carries every tool call, so it also gives each beat its cause, Trine its site and the thought bubble its text. Runs started from the page need no hooks. Hooks remain the way to watch a session started in a terminal, later. The installed Claude Code has the flags for this. It is untested.

Two targets, in order. First, small greenfield projects: the prompts used for the Hazel demos (the vector scene, the turn-based game, the crafting system, the dungeon with modules) in an empty dune project. This is the like-for-like comparison with Hazel. Then the Hazel repository, 552 modules and about 158,000 lines.

What the first runs answer. Whether an agent editing OCaml as text gives a picture like Hazel's, or whether code arrives in one chunk and is only replayed. My guess is in between: a first file written whole, then smaller edits. Each prompt is run plain and with a nudge toward small steps and inline tests.

  1. Index a small hand-written OCaml project, the vector scene ported, to graph JSON. Check it by hand.
  2. Copy the Hazel-free canvas files into this repository behind the graph record. Render that JSON on a static page.
  3. Watch files: a hand edit re-indexes and the existing score plays. A broken file keeps its last good picture. Selecting a node shows its code.
  4. Chat pane: the sidecar runs Claude Code headless and relays it; the stream labels each beat. Record and replay a trace.
  5. Run the vector prompt in an empty project and watch, then the other demo prompts. Compare with the Hazel recordings.
  6. Point it at the Hazel repository.

Where it stands, 11 November. Steps 1 to 5 run for the vector prompt, and the page shows Hazel's canvas, ported (17 of its files byte for byte), beside the chat, in Hazel's styling with a dark mode. It also opens existing projects, Portolan's own code included (./portolan serve .), one module at a time: a picker in the top bar chooses the module, and types from other modules are drawn faint. A project's conversation carries on across restarts. Portolan's own code is ReasonML, in small modules with interfaces. A recording of the first real run plays in the browser. Two runs of the vector prompt so far, one each, so read these as anecdotes:

It is neither one chunk nor Hazel-like. The agent works in the steps the prompt names, and each step lands as a batch. The nudge makes the batches smaller while the program grows. In the final refactor it backfires: changing a type that everything uses breaks the build until the last use is fixed, and doing that in ten small edits kept the picture frozen for over half the run. That is the case for changes that land whole, and for marking each definition as broken or fixed during a refactor in place of freezing the picture.

Not measured yet: how fast ocamllsp answers on a 2,000-line Reason file mid-edit. If too slow, a parse-only reader goes in front of it.

Next: what the first runs will ask for

Working on Portolan in Portolan. The aim is to move some of Portolan's own development out of the Claude Code app and into this page. It draws its own code now. What the chat pane still needs for that: replies as formatted text (done) and as HTML, an approve button for commands outside the allowed list, and the agent's questions shown as questions. Every gap found this way goes in this list.

Something valid to draw. Hazel always has a well-formed program to draw. An agent editing OCaml as text can leave files broken for long stretches. The first build redraws the modules that still compile and, in the others, marks the definitions holding an error and keeps the rest as they were. Beyond that there is a ladder of influence over the agent: a prompt suggesting small steps and holes, tools it is encouraged to use, tools it must use, our own harness. Each rung buys more valid states and costs generality. The first runs, and your session logs, will say how far up is needed.

The edited view. An agent holds far more in its head than a person, so what you are shown is an edit of what is there. Four kinds: omit (show a sub-diagram), fold (a hull for its contents), rank (only the arrows that carry weight), and merge (several types as one node where their differences do not matter, a quotient). Merge is the strongest and can wait. Every edit leaves a visible trace, a count or a seam, and opens in place, so the picture is edited and still honest. The Hazel repository needs fold and rank at once.

Layout from square one. The port keeps Hazel's layered layout. It tangles too often, so layout is the first thing to rethink, possibly with different methods for different situations. To try: module regions placed first and nodes inside them; a template per module with its main type in the middle; a method per level; a budget, so a view folds until it fits. Hazel's history is a corpus to compare them on. Hazel's own layout survey argued for refining the layered engine, so it should be reread first. Measured on Portolan's own code: a module of 75 definitions lays out in 0.6 seconds, but the layout re-ran about 20 times in five seconds; the whole project, about 500 nodes, blocked the page for 65 seconds. Cost grows roughly with the cube of size, so one module at a time is a requirement for now, and the repeated runs are the first thing to fix.

The main bets

Interfaces as the map. A module is drawn by its signature, with the implementation folded inside. The reason is review: if the signatures a change touches are right and the tests behind them pass, the implementations often need no reading. Anil Madhavapeddy argues the agent's side in a post and an OCaml Workshop paper: type-check the .mli files for a whole system first, then hand an agent one module at a time, and let abstract types enforce the design. On the canvas that is a set of rims with empty interiors that fill in. Hazel has 52 interface files for 552 modules. For the rest the sidecar can derive the used interface, the members other modules reference, as a draft .rei.

How modules relate. Not drawn yet: functors, include, module aliases and nested modules beyond hulls. A proposal to argue with. A functor is a module with a socket, the signature it expects. Applying it gives a region that points back to the functor and shows what filled the socket, without copying its members. include is the same pointing back with the members shown as the including module's own. These want designing together, and with Hazel's Modules II, before either side builds them.

Change sets as pictures. The canvas works by comparing snapshots. Compare against a fixed base and it is a diff view: a session, a branch, a pull request, last week. It is a diff of definitions and interfaces, with the text diff one step down. The same marks serve live and afterwards, sorted by how much reading they ask for.

History as material. Git history and merged pull requests are coarse and complete: any commit is a snapshot. Claude Code session logs are fine-grained and chronological. Replaying a log's edits onto its base commit turns a past session into a trace without running an agent again. Open: what to keep from now on, and whose logs. A trace needs only graph snapshots, tool names and paths, so it can leave the conversation out.

What each agent has seen. For a given agent each definition is unseen, listed, read or edited, raised by what its tool calls returned. The canvas should be faithful about this, because it is how you understand an agent's context. You switch between that and your own edited view.

Several agents. On the canvas an agent has a body (its Trine), a history (its change set) and relations to other agents, which are open how to draw. Histories can be compared: agents usually work in separate worktrees, so each is a diff against a common base, overlaid with a colour each. What to surface is where they meet: two inside the same hull, or one changing a signature another depends on. The first build keys its log by agent so this stays open.

Further out

Voice and ink. Voice, pointer and ink on one clock, as spall-multimodal has. Pointing words bind to what was selected when each was spoken; the Stratum voice gateway does this today. Ink anchors to nodes and follows them as the layout moves: an arrow between two nodes, a loop around several, a line across a hull, a strike. A turn reaches the agent as text with every reference resolved.

Editing by definition. The verbs from editing-in-the-large (insert, replace, delete, move, rename, open, close, a folded map) served by the sidecar over MCP. Files stay the store, and the structure is what edits go through: the kernel turns a verb into checked text splices, while bash and plain edits stay legal. On Hazel's agent in October these verbs used about 22% fewer input tokens and 30% fewer calls. OCaml adds work: every edit has an .mli side, moves cross files, and the check costs a build. This is the top of the ladder of influence above.

Properties on the diagram. The canvas is close to a categorical diagram, so an equation between functions is two paths between the same nodes that are claimed to agree. You mark the face between them. It is stored as a property test that names both paths, so existing property tests can be drawn too; Hazel's QCheck tests are a ready supply. An agent writes the generator and the test, and the mark carries the evidence the way a pip does.

Slices of a definition. When drilling down reaches code, show only the arms that matter and count the rest. Which arms depends on why you opened it: the ones a change touched, the ones that mention a selected type, the ones that contribute to an error, the ones a test actually took. The last is dynamic; coverage data gives it cheaply.

Tandem

Keeping in line with Hazel

What is shared is a contract: the graph record, the trace format, the principles document and the CSS token names. Code starts as a copy here, with agent-canvas untouched. If both sides want the same change twice it can become a shared library, and if this app pulls ahead Hazel can mount its canvas. The table above is where the two are kept in line: a direction is designed once before either side builds it. Entry identity here is path plus content hash, definition-level in the spirit of Arbor.

Look

Hazel's look, for now

Decided for now: imitate Hazel, pacing and animation included, and iterate after. Changes from Hazel so far: yellow in place of the green accent, chrome in one colour family, square bar tabs, and a dark mode after the Graphite scheme. The colour schemes study shows fifteen candidates on the whole app, six of them Graphite with an accent, and lets you change any colour.

Name

Portolan, for now

A portolan is a sailor's chart: coasts drawn in detail from the routes actually sailed, interiors left blank. It reads two ways here. The routes sailed are the agent's footprint. The drawn coast with a blank interior is a module shown by its interface. The name is already used by a geospatial data project, a small code-atlas repository and an AI consultancy, so it may need to change. In reserve: Trellis, Coppice, Atlas, Selvage, Signet, Asterism, Promptbook, Armature, Maquette, Caravanserai, Vitrine.
