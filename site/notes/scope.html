An agent canvas for OCaml code bases

A way of working with a code base at a level above the text, with the text always one step down. The starting point is Hazel's Constellation canvas, pointed at ordinary OCaml and Reason projects. What it is for is still being worked out. This page fixes a small first build and sketches where it could go.

In short
  • First build. The parts of Hazel's canvas that translate, for a dune project: types as nodes, functions as arrows, modules as hulls, tests as pips, Trine, replay, and a click through to the code. It works on a repository at rest, on a recorded run, and live beside Claude Code.
  • How. A native OCaml sidecar turns the project into the graph record Hazel's canvas already draws. The canvas code is copied behind that record, free to be shared with Hazel or to diverge later.
  • Directions, sketched and not in the first build. Interfaces as the map, change sets as pictures, several agents at once, voice and ink, editing by definition, properties on the diagram.
  • This page is kept current. It records the scope as it is talked through: your directions, and ones proposed here, marked as such.
Purpose, unsettled

Orders of reading

A working statement, to be revised: the canvas gives a code base several levels, and lets you stay at the highest one that answers your question. Each level shows the one below folded, and opens it on demand, down to the code. It could turn out to be a main way of engaging with code, and the first build should not close that off.

Three things this should not shrink to:

  • Only a first glance. The demo framed it as a first-order alternative to the transcript. The emphasis is better put on having orders at all, and moving between them.
  • Only live. Watching the agent work is the fun part. As a tool it matters as much afterwards: what did yesterday's session do, what is in this branch, what is this code base.
  • Only one agent. The broader subject is people and agents cooperating in one code base, including a few agents at once.
First build

What Hazel has now, for a dune project

Hazel's canvas is about 27,000 lines, of which roughly 15,000 have no Hazel dependencies: layout, score, player, camera, Trine, bubbles, traces, CSS. Everything downstream of one function, CanvasGraph.extract, reads a plain record of type nodes, function arrows, tests, module paths and error flags. The canvas never reads edit operations. Each step it gets a new snapshot of that record with a cause and a site, and derives the choreography from the difference. So the port is a new producer for that record, plus a copy of the Hazel-free code.

Where the graph comes from. The sidecar asks the project's own ocamllsp, which vendors Merlin. It reads .re through the Reason reader, so Hazel works on day one. It recovers from errors one item at a time, so a half-edited file still yields its other definitions. And it is whatever version the project's switch has, so our binary is not tied to a compiler version. dune describe gives libraries. A watch build beside it keeps cross-module types and the occurrence index fresh.

How it hears about the agent. Two signals, joined by time and path. The file watcher is ground truth and is enough alone: any change by any tool produces a new snapshot. Claude Code's tool-call hooks post to the sidecar and say which agent did it, where, and what it read. Codex hooks have nearly the same shape, and OpenCode has an event stream. A trace records snapshots and causes, so a run replays in a browser with no OCaml toolchain.

Scale. Hazel is 552 modules and about 158,000 lines, so the first build opens at the library level with hulls collapsed, and frames what was touched.

  1. Index one Hazel library to graph JSON. Check three modules by hand.
  2. Copy the Hazel-free canvas files into a new repository behind the graph record. Render that JSON on a static page.
  3. Watch files: a hand edit re-indexes the touched module and the existing score plays. Selecting a node shows its code.
  4. Claude Code hook adapter: cause labels and Trine's site, keyed by session. Record and replay a trace.
  5. Run a real task on Hazel and look at it together, live and then from the trace.

Not measured yet: how fast ocamllsp answers on a 2,000-line Reason file mid-edit. If too slow, a parse-only reader goes in front of it.

Interfaces as the map

A module is drawn by its signature. The implementation is folded inside the hull and opens on demand. The reason is review: if the signatures a change touches are right and the tests behind them pass, the implementations often need no reading.

Anil Madhavapeddy makes the matching argument from the agent's side in a post from October and an OCaml Workshop paper. Write and type-check the .mli files for a whole system first, then hand an agent one module at a time, since it fills a small well-specified hole better than it handles a large code base. Abstract types then enforce the design: an agent that reaches around an interface is stopped by the compiler. On the canvas that workflow has a natural picture: a system designed interface-first is a set of rims with empty interiors, drawn like Hazel's hole-bodied arrows, and implementation fills them in. His post says interfaces for this kind of work are only beginning, and points to Hazel.

Hazel has 52 interface files for 552 modules. For a module without one, the sidecar can derive the used interface: the members other modules reference. That is a draft .rei, which makes the tool a way of moving Hazel toward interfaces as well as reading them.

Change sets as pictures

The canvas already works by comparing snapshots. Compare against a fixed base and it is a diff view: a session, a branch, a pull request, last week. It is a diff of definitions and interfaces, with the text diff one step down on any marked node. The same marks serve live and afterwards, sorted by how much reading they ask for.

Several agents

On the canvas an agent has three parts. A body: its own Trine, showing where it is and what it is doing. A history: the change set it has made. And relations to other agents: who started whom, who is messaging whom. How to draw the relations is open. The history is the part that can be compared. Agents usually work in separate worktrees, so each history is a diff against a common base, and the canvas can overlay a few of them, with a colour and a sidebar lane each. What the overlay should surface is where they meet: two agents inside the same hull, or one changing a signature another's work depends on, before the merge finds it. Start with two or three. Hook events already carry a session id, so the first build keys its activity log by agent. That is the only part of this that touches the first build.

Who knows what, and what you are shown

Two questions share the canvas. What does the agent have? Each definition is unseen, listed, read or edited for a given agent, raised by what its tool calls returned. The canvas should be faithful about that, because it is how you understand an agent's context. What should you be shown? Much less, by default. An agent holds far more in its head than a person can, so your view is an edited one, and you can switch between the two.

The edits come in kinds. Omit: show a sub-diagram. Fold: show a hull for its contents. Rank: show only the arrows that carry weight. Merge: draw several types as one node where their differences do not matter to the question, a quotient of the diagram. Merging is the strongest and can wait. The rule for all four is that a simplification leaves a visible trace, a count or a seam, and opens in place. The picture is edited and still honest.

Talking back without typing

Voice, pointer and ink on one clock, as spall-multimodal already has. Pointing words bind to whatever was selected when each was spoken; the Stratum voice gateway does this today with local whisper.cpp and could run unchanged beside the sidecar. Ink anchors to graph entities and follows them as the layout moves: an arrow between two nodes, a loop around several, a line across a hull, a strike. A turn lands in the sidebar and reaches the agent as text with every reference resolved, through a hook at its next tool call.

you · 14:02:11 · voice + ink

“this → Outline.of_term should take that → Statics.Map.t as well, and these two → loop A belong in one module”

sent to the agent: Outline.of_term should take Statics.Map.t as well. Ink loop A encloses Zipper.t and Segment.t: these belong in one module.

Editing by definition

The verbs from editing-in-the-large (insert, replace, delete, move, rename, open, close, a folded map) served by the same sidecar over MCP, so they run inside the harness already in use. Files stay the store, and the structure is what edits go through: the kernel turns a verb into checked text splices. Bash and plain edits stay legal and reach the model the same way. In October's A/B on Hazel's agent these verbs used about 22% fewer input tokens and 30% fewer calls. OCaml adds real work: every edit has an .mli side, moves cross files, and the dependents check costs a build. A shell with outline, stacked definitions and chat comes after that. Whether it embeds OpenCode or runs a small loop of ours turns on whether we need to control exactly what the model sees.

How much to shape the agent

The canvas is not independent of how the agent works. Hazel's trick is that the program is always well-formed enough to type-check and run, so there is always something to draw. A harness editing OCaml as text can leave files unparseable or ill-typed for long stretches, and a canvas that goes blank or jumps during those is useless. There is a ladder of influence: nothing; a prompt or skill suggesting small steps and sketching with holes, interfaces first; tools the agent is encouraged to use; tools it must use; our own harness. Each rung buys more valid intermediate states and costs generality. Two things come before climbing it. The canvas holds the last good state of each definition and marks what is in flux, so it never breaks and never pretends. And the session logs can tell us how often, and for how long, past sessions actually left Hazel broken. Drawing a repository at rest, change sets and interfaces do not depend on any of this. Live quality, attribution per definition and exact knowledge of what the agent has seen do.

Properties on the diagram

The canvas is close to a categorical diagram, so an equation between functions has a picture: two paths between the same nodes that are claimed to agree. You would state one by selecting the two paths and marking the face between them. It is stored as a property test that names both paths, so the canvas can equally draw the property tests a code base already has; Hazel's QCheck tests are a ready supply. An agent writes the generator and the test, and the mark then carries the evidence, the way a pip does for a unit test. Round trips, idempotent orbits and invariants are the same idea in smaller shapes. Proof tools would attach at the top of the ladder. The canvas only has to show that a property exists and how well supported it is. Laws between exported functions belong at the rim, where a reviewer reads them, and a change set that breaks one shows as a refuted mark.

Slices of a definition

A side note for when drilling down reaches code. The stance is to be selective about what is surfaced: opening a definition should not put a multi-page match in front of you. Folding to definitions is already a coarse slice, and the same folding can go one level finer, to the arms that matter, with the rest shown as a count. What matters depends on why you opened it. For a change: the arms that changed. For a selected type: the arms that mention its constructors. For an error: the parts that contribute to it, which is what type slicing computes. For a run: the arms a test actually took. That last one is dynamic, and a full version means work in the runtime, but coverage data per test gives arm-level answers cheaply. The agent's map could use the same slices to save tokens.

History as material

Once an OCaml code base can be drawn, Hazel's past becomes data. There are two sources, with different grain. Git history and merged pull requests are coarse and complete: any commit is a snapshot, any pull request a change set. Claude Code session logs on your machine are fine-grained and chronological: each read and edit in order, which is enough to rebuild what an agent saw and did. Replaying a log's edits onto its base commit would turn a past session into a trace, with no agent run again. That gives after-the-fact viewing early, and test material for the first build. Open questions: what to keep from now on, and whose logs. A trace needs only graph snapshots, tool names and paths, so it can leave the conversation out.

Layout from square one

The port keeps Hazel's layered layout so that the first build is a port. After that, layout is the first thing to rethink, because the current engine ends in a tangle too often. There may be several algorithms, each used where it suits. Candidates to try: place module regions first and nodes inside them, where today hulls are drawn around nodes placed without them; a fixed template per module, its main type in the middle with orbits and exported arrows at the rim; a different method per level of the ladder; and a budget, so a view never holds more than it can lay out cleanly and folds or ranks until it fits. Hazel's own history gives a corpus to compare them on, with crossings and hull overlaps counted. Hazel already has a layout research survey and a layout lab to start from.

Names

Portolan, for now

A portolan is a sailor's chart: coasts drawn in detail from the routes actually sailed, interiors left blank. It reads two ways here. The routes sailed are the agent's footprint. The drawn coast with a blank interior is a module shown by its interface. The name is already in use by a geospatial data project, a small code-atlas repository and an AI consultancy, so it may need to change. The rest of the list is kept for that case.
